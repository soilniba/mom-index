# 收盘后持续轮询（2026-11-05）

## 需求原文

> 那就改成每天。下午3点收盘之后。嗯，固定间隔时间去查一查，什么时候查到了，什么时候就更新如果一直查不到，就一直不更新，如果是说已经到第2天了还没查到，就就把两天的这个查询合并起来，反正就是3点之后开始查，查到了就更新，然后停止再去查，没有查到就一直查询，但是呢也不要调用接口太频繁，导致那个。平台封号。然后如果查到第2天还没有查出来，就跟第2天的查询合并。两天的一起查，然后查到了一一起更新。

用户随后指定：

> 每小时一次太慢了吧，10分钟一次差不多

## 明确行为

- 每个交易日北京时间15:00收盘后首次加入当日任务；之后每10分钟检查未完成日期，包括夜间和周末。
- 下一交易日收盘后将新日期加入同一个队列；合并请求范围，不建立多个并行轮询任务。
- 某日完整后更新网页、发送ETF图卡，并移出待查队列；未完成的日期继续保留，没有尝试次数上限。
- 全部完成时后续定时唤醒不调用行情接口；下一交易日收盘后恢复。
- 尚未齐全时保留网页已有数据，不反复发送陈旧ETF图卡。
- 有新完整日或补齐历史缺口时发布；同批完成多个日期只发送一张最新图卡。
- 不加入交易所补源，继续使用stock_data/Tushare；公式、成员核验和methodology v2保持原样。

## 实现选择与限频

采用已有systemd user timer每10分钟唤醒一个短任务，不维护常驻sleep循环；重启时补跑。
10分钟是用户明确指定；份额/净值事实请求之间再留至少2秒。
更新器按最早待补日期到最新待补日期合并取数，仅合并待补日期的结果，已完成日期不回退。
不再每轮重拉45日历史。原23:30宝妈报告保留，自动发送阶段跳过ETF，避免重复取数与推送。

## 持久化与恢复

- `data/etf_poll_state.json`：开始追踪日、已入队的收盘日期、待查日期、上次尝试时间及待发状态。
- 初始追踪日为既有最新完整日之后；不把2024年以来历史研究缺口加入新任务。
- 入队、上次尝试和发送待办在联网前原子保存；异常退出后不会丢失待办。
- 成功保存完整数据后移出查询队列；网页/飞书失败仅重试发布，不重新取已经齐全的数据。
- 进程锁防止任务重叠；持久化10分钟时段，同一时段重复启动不联网，避免timer秒级抖动拖成20分钟。
- 密钥沿用systemd user manager环境，不写入仓库、状态文件或日志。
- 所有历史更新入口在原子替换前共用目录锁并比较原始快照；慢手动响应遇到较新文件时拒绝覆盖，
  避免把轮询已补齐、已移出队列的日期重新抹成缺口。

## 接口分工

- `analyzer.etf_oi.update_history(path, end_date=None, *, pending_dates=None,
  request_interval_seconds=0)`：默认保留既有手动更新；轮询时仅合并指定日期，无完整值则原文件不变。
- 共享API`fetch_csi300_etf_position_history(start, end, *, request_interval_seconds=0)`：
  允许调用者为份额/NAV事实函数设置最小请求间隔；默认不改变其他消费者。
- `scripts.notify_etf_oi.send_etf_oi_card(data)`：只生成并发送指定v2数据的图卡，返回真实发送结果。
- `scripts.poll_etf_oi.run_poll(data_dir, now=None)`：入队、限频、更新、网页发布、通知及状态恢复；
  正常未齐返回0，实际错误返回1，下一轮继续；CLI使用同一入口。

## 安装与运行

安装仓库内的两个unit到`~/.config/systemd/user/`，执行：

```bash
systemctl --user daemon-reload
systemctl --user enable --now mom-index-etf-poll.timer
systemctl --user start mom-index-etf-poll.service
systemctl --user list-timers mom-index-etf-poll.timer
journalctl --user -u mom-index-etf-poll.service -n 20 --no-pager
```

服务为单次任务，最长9分钟；异常由下一轮10分钟唤醒恢复，不在一个进程中立即循环重试。
状态文件与锁属于本地运行产物，不入git。完整历史文件缺失或state损坏时先排查日志，
不得为恢复任务而删除仍包含旧待补日期的state。
