# 共享接口与调用方核查（2026-11-05）

## 需求原文

> 看看 stock_data 里这个指标的接口有没有类似的问题，还有其他调用这个指标的地方有没有类似问题

## 核查范围

全项目代码搜索定位到两个实际消费者：mom-index和chief_analyst。
共享计算入口为stock_data.fetch_csi300_etf_position_history；只读冻结成员API保留既有合同。

| 入口 | 当前行为 | 核查结论 |
|---|---|---|
| stock_data公开历史API | 超冻结范围总是先刷新live参考 | 已归档完整历史会被live源故障阻断，需修复 |
| mom轮询 | 10分钟待补队列、完成后移出 | 完成日期后被手动刷新退化为缺口时，队列未恢复，需修复 |
| mom网页/飞书 | 共用v2历史与原子发布 | 日期/缺口提示及v2保护正常 |
| Chief A股报告 | context→gateway→stock_data | 无私有缓存；默认截至今天为既有明确行为 |
| Chief Web/CLI工具 | 同一context及工具注册表 | 请求内失败结果被去重阻止重试，需小修 |
| Chief常驻Web服务 | 11月1日启动的worker | 共享代码更新后未重启，需通过systemd重启验收 |

## 最小修复设计

1. stock_data先验证已有目录与逐日原始成员档案；已覆盖的历史请求不强制访问实时参考源。
   真正缺参考的日期仍刷新，损坏档案继续报错，不引入派生比例缓存。
2. 轮询每次读历史时，将追踪区间内已退化为缺口的日期重新入队；原入队日期和10分钟限频保留。
   若待发日期不再完整，撤回该待发并重新补查；不发送陈旧数据。
3. Chief仅为该ETF工具的临时不可用结果允许一次相同参数重试，成功结果仍去重；其他工具不变。
   修订过期的生产解释器说明，最后用systemd重启Web服务，使长驻进程加载当前共享模块。

## 边界

- 不改公式、methodology、评分、择时、仓位和其他工具策略；不增加交易所补源。
- 当前共享API按调用方明确日期返回事实，不擅自裁掉未收盘日；Chief默认今天不作为本次bug修改。
- 原始档案仅证明对应日期，不能把当前成员反向填到缺档日期。
- 不将2024年以来研究缺口纳入轮询；仅恢复tracking_start至queued_through内的退化记录。
- 测试全部隔离路径、mock源及消息边界，不发送飞书测试消息、不批量探活公告。
