# ETF 网页版本兼容与缓存修复

## 问题与证据

2026-11-01 用户报告生产 dashboard.html 提示“ETF 数据暂不可用”。
全新桌面/手机浏览器正常，线上 HTML、JS、v2 JSON 均为 200。
用实际上线过的 v1 HTML 搭配 v2 JS/JSON，可稳定复现相同提示：
旧页面没有 `etf-oi-valuation`，脚本写入空节点触发 TypeError，外层 catch 隐藏指标。
旧 JS 还会拒绝 v2 数据；原脚本地址无版本参数，HTTP 响应无缓存策略。
尚未取得用户浏览器缓存，不能断言用户具体命中了哪种组合。

## 修复设计

- 新页面引用带发布版本的 ETF 脚本；新版脚本兼容缺少估值说明节点的旧页面，
  在基金样本说明后补建说明节点，继续严格要求 v2 数据。
- 用标准库静态服务包装现有 http.server，为响应增加 `Cache-Control: no-cache`，
  保留 Last-Modified/304 重验证、8765 端口与 IPv4/IPv6 接入。
- 已经完整缓存的旧页面和旧脚本无法由服务器追溯修改；本次交付提供带版本的
  页面链接以获得新 HTML，之后响应按新策略重验证。

接入审计还发现 `--no-refresh --preview` 和 `publish_etf_oi` 未校验口径，
临时目录实测能将 v1 归档发布为当前网页数据；为这两个边界补 v2 校验，
拒绝旧版时不改已有文件、不发送通知。
没有可读缓存时仍发送原有明确失败告警，不携带旧比例。

仅修改发布兼容、缓存及版本校验；计算公式、数据、采集任务均不改。
选择源站响应头而非浏览器 meta 标签，避免依赖无效的缓存指令；
选择标准库包装而非调整远端 nginx，便于版本控制和本机回归。

## 实施与验收

1. 浏览器回归先复现缺节点错误，再验证旧页面仍显示 v2 比例及估值说明。
2. 使用真实 HTTP 缓存验证旧脚本缓存不会污染新页面；拒绝 v1 数据保持有效。
3. 验证 HTML/JS/JSON 的 200 与 304 均携带重验证策略，运行项目测试。
4. Push-Guard 审查后合并，更新 systemd 启动入口并重启 web；公网桌面/手机验收。
5. 检查 stock_data 缓存隔离、chief 分析/Web 工具与 mom 通知/绘图/同步入口。

本机回归已先观察到旧 DOM、旧脚本缓存两项失败；修复后浏览器三项及 HTTP
200/304 三项全部通过，旧口径 JSON 仍被拒绝。后续改 ETF 脚本时必须更新 HTML
脚本版本参数；不能仅依靠新响应头清除已经存在的旧缓存。

## 其他接入点检查

| 入口 | 核查结果 |
|---|---|
| stock_data | 每次返回 v2，无派生比例 SQLite 缓存；目录/成分版本中的 v1 是参考资料版本，不是方法版本 |
| 共享原始数据 | daily_basic/adj_factor 截至10-30，683个交易日日期与已发布历史一致；本轮不重新联网采集 |
| chief_analyst | 网关透传共享 API、格式器严格拒绝非 v2；web 进程启动晚于 v2 代码发布 |
| mom 通知/预览 | 正常图卡已校验 v2，手动预览存在绕过；补入口校验，旧版不上传、不发送 |
| mom 数据同步 | 原先纯字节复制可覆盖 v2；改为同一次读取后校验并原子发布 |
| mom 绘图/pipeline | 图函数接收已校验记录，pipeline沿用通知入口；保留合法v2缺数据告警 |

chief 的分析脚本、stock_context、聊天工具和 Web 回答均复用同一格式器；
前端只渲染消息文本，没有独立 ETF JSON/脚本字段依赖。实际 `/`、`/api/models`
均200，返回页面哈希与磁盘一致；相关实现相对前次线上验收无改动，本轮未额外调用LLM。
旧会话保留历史文字，不回写为新口径。

最终全库96项通过（仅原有 Pillow 弃用警告）；通知/同步先观察到11项预期失败，
修复后定向28项通过。测试只用临时数据，没有发送飞书或重跑生产采集。

## 经验

数据迁移发布必须检查返回用户的旧页面缓存；只测全新浏览器不能覆盖版本错配。
新增展示节点不得让同一口径的完整数据整体不可用。
